New mobile game (in development)

Fundora · Unity 6, URP · lead programmer

I wrote about 900 of its 1,230 commits.

The game hasn't been announced, so I'm leaving out its name and how it plays. This is about how it's built.

My part
  • I wrote all the game rules as plain C#: no MonoBehaviours and no Unity types. The board is a graph, pieces can take up more than one cell, and every move is resolved and checked before anything on screen changes.
  • The visual side only reads the rules and never writes back to them.
  • I built the level editor (a tile palette inside Unity), tools that generate the game's art from source files, and a level validator.
  • I set up PlayMode tests that drive the real scene. Checks we used to do by hand after every change now run automatically.
Why the switch to 3D took a day

From day one the board used Vector2Int, and only four small functions converted to world space. Weeks later we decided the game had to be 3D. Because the rules didn't know anything about rendering, the switch took a day. I also wrote a test that runs through all 3,264 combinations of piece shape, direction, move and position. Most of the failures it reported were bugs in the test itself, but one was a real edge case, and it's a permanent test now.

Production pipeline

Studio process and tooling · my own project · 2026

The studio's newer games were started with it. I wrote all of it.

After my first game at the studio I wrote down what had worked and turned it into a process anyone at the studio can follow to build a mobile game with an AI coding agent. Designers who don't code use it to start new games. The main idea is that every step ends with something a person can check.

What's in it
  • A command-line wrapper for Unity that compiles, runs tests, and runs editor methods headlessly. It works on a copy of the project, so you can keep the Editor open. The agent and the person get the same pass or fail.
  • Phases from research to release, each with clear exit criteria. There's one hard stop: a person has to confirm the table of game rules before anything gets designed.
  • Setup scripts for new projects, a release script that strips the debug tools out of player builds, and a small Python tool that compares video frames to help read mechanics from gameplay footage.
  • Written conventions for code, Unity, git and art, and setup guides for designers in English and Persian.
Why the rules get signed off first

Early on I misread a game's core rule, and the mistake made it into four documents before anyone caught it. Since then the rules table has to be signed off first. I also made one strict rule for the agent: it never reports a result it didn't actually run. Each session ends by updating a handoff doc, so when the context runs out the next session starts from the notes instead of repeating old mistakes.

Prototype to production (in development)

Fundora · from an HTML prototype to Unity

Every level passes the built-in solver.

A designer built the first version of this game in HTML, and I turned it into a Unity game. It's unannounced, so no name or gameplay here.

My part
  • I ported the prototype's physics simulation to C#. On every level it reaches the same result as the prototype at every step, with final positions within 4e-12 units.
  • I built a Unity level editor that works like the designer's HTML editor, including a phone preview that runs the real game code. It reads and writes the prototype's level file without changing a byte.
  • I added a solver, a "check all levels" button, and a check that refuses a broken level when it loads. I also generated the art from the prototype's drawing code and made a Luna playable ad.
Why I kept the prototype's file format

Because I kept the prototype's file format, the designer didn't have to change how they worked. On the first day they edited a level and added a new one in Unity, and nothing broke.

How I work

Rules first, visuals second

Game logic is plain C#. If I deleted every model and sprite, it would still compile and the tests would still pass.

A rule is done when a test says so

For tricky geometry I check the maths in a quick Python script before writing any C#.

No field without a reason

If no rule reads a value, I take it out before other code starts depending on it.

AI helps, I own it

Agents work inside rules and checks I set up. I review everything that ships and can walk you through any of it.
